### 全自动（Autopilot-full）

**verdict 归你，PR 绝不归你。每个 PR 由一名负责人从构建带到合并。在你的 swarm（蜂群）证明即将合入的代码之前，什么都不合并。这个 swarm 自己没写过这段代码。**

一份 verdict 只覆盖一份补丁，一次变绿的 CI 只覆盖一个 head。第 4 步的完整 swarm 只跑一次，只有大改才再跑。`playbooks/shipping.md` 的 patch-id 规则可以沿用某条 lane 的结果。每个新的 head 都要有自己的绿色 CI。

1. **操作者的关卡优先。** 授权只覆盖队列里的条目。操作者点名归自己的，以及队列以外的 PR，都停在 merge-ready。要求把计划说出来，并不等于开工。
2. **每个 PR 派一名负责人，并把工作放在替补找得到的地方。** 整个项目只定一次托管平台。默认是 GitHub CLI（`gh`）。`command -v origin` 成功，并且 Origin 能解析这个仓库时，每次 PR 操作都用 `origin pr`。否则继续用 `gh`，并记下这次回退。**绝不**要求 Graphite（`gt`）。每个负责人是一个 Cursor cloud agent。它负责构建，按 `playbooks/opening-a-pr.md` 开 PR，在真实产物上证明改动，按 `playbooks/babysit.md` 看护到全绿，第 4 步和第 5 步都放行之后才合并。

   尽早开 PR，让 CI 和 bot 跟工作一起跑。代码要等 slop（AI 腔、套话）清掉（`cursor-team-kit` 插件里的 `deslop` skill，即 `/deslop`），并且跑过 `/pstack:no-comments`，才算就绪，所以完整 swarm 跑在做完的代码上。然后 rebase 到当前 trunk，自证之前先报 code-ready 的 head，这样验证跑在补丁即将落上去的那个基点上。之后每个 head 都要报。自证、CI、babysit 都完成了，再报 merge-ready。修复轮次留在这个基点上，除非 trunk 冲突或把 CI 弄坏，因为每次 rebase 都会让 CI 重跑。code-ready 那次推送之前，以及之后每次需要验证者的推送之前，在已经提交的 head 上跑仓库针对改动路径的检查。

   就当这台 VM 会死。启动后不久就推送，并按 **show-me-your-work** skill，在根代理的存储目录里开始写决策记录（路径在系统提示词里）。每个值得留下的单元之后再推一次。谁派出子代理，就把子代理的 id、状态，以及按同类以往运行估出的卡住时限，记进那个存储目录。父代理要是死了，根代理还能探到它。只 force-push 自己的分支，`--force-with-lease` 钉在你上次推送或接手时的那个 SHA 上。遇到不是你做的推送，停下来，报告给根代理。
3. **负责人从 trunk 并行开出去，绝不叠成 stack，** 这样每个 PR 各自合入。
4. **swarm 只验证一次。** 完整 swarm 在 code-ready 的 head 上跑一次。只有新行为、一次重新设计，或一大块新 diff，才再跑完整 swarm。rebase、解决合并冲突，或小修复，在新 head 上只派一个验证者。在 code-ready 的 SHA 上，按 **swarm** skill 扇出互相独立的验证者。它们重跑关卡，通过对应的 control skill（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或一个写明名字的驱动，在真实界面上实跑，证明关键行为，并审一遍 diff。没有 live lane，或者你还没审 merge-ready 报告里的回执，verdict 就不算干净，因为没有哪条 lane 会相信自己没核对过的说法。

   每条已经证实的发现，不管 lane 给它贴了什么标签，一次交给负责人向前修，并带一条 red test，覆盖所有有同一缺陷的位置。trunk 上没有这个 PR 也存在的缺陷，记在 trunk 上，不拿来挡这个 PR。这个 PR 抄来的、或新碰到的，算这个 PR 自己的。**绝不**自己推修复，因为每个分支只有一个写入者。负责人卡住了，就换一个。
5. **负责人只合并你验证过的、并且在它即将落上去的 trunk 上测过的东西。** 单凭 CI 变绿，**绝不**授权合并。swarm 的 lane 开跑之后，合并准备把分支 rebase 到当前 trunk，报新的 head，等 CI 变绿。

   合并前一刻，先 fetch trunk，看它的改动会不会影响这份补丁。trunk 每动一次就 rebase，永远做不完。即将合入的代码还没测过时，才 rebase 并等 CI。例如有冲突、两边改了同一个文件，或者决定这个 PR 跑哪些检查的配置变了。两边都改了 lockfile 时，如果在合并结果上一次冻结安装能通过，而且这个 PR 改过的包在那里的解析和 head 上一样，就不必 rebase。这次安装测的就是即将合入的 lockfile。安装失败，就说明 rebase **必须**把它修好。trunk 改了补丁的调用方，或改了补丁所依赖的东西（它调用的代码，或某个依赖的版本）时，在合并结果上跑这份补丁的检查，通过就合并。其余情况直接合并。如果 trunk 会迫使合并准备之后再来第三次 rebase，就停住，报告给根代理，由它来安排这些撞在一起的工作。
6. **跑根代理这一层。** 任何把关卡放宽的事，例如上调预算或加一条允许名单，都要先有验证者的证明，再由你重新会签，因为想变绿的是负责人。授权已经覆盖审批时，这次会签就是审批。负责人对它的记录要指向你的会签，供一条 lane 来核对。关掉的检查，或软失败的检查，一律拿掉，因为它不再守卫任何情况。托管平台强制的审批，**绝不**代批，也**绝不**绕过，因为会签覆盖不了它。

   操作者说开始时，设上 `/loop 1h`，一直审计到委派出去的工作一项不剩。长跑会漂移，agent 会一声不响地卡住。每次巡检从 trunk 重读这份 playbook，并把漂移补上，例如没报告的 head，或没记录的 agent，让它的负责人记下来。漂移是记录上的缺口，不是卡住。巡检要探到每一个 agent，一直到最底层的 lane，只按副作用判断，因为状态文字和摘要会把卡住的子代理藏住。agent 报错、开不了新回合，或者过了卡住时限仍没有任何新东西，就算卡住。到第一次巡检时既没推送、也没写一行决策记录的负责人，也算卡住。正在等你或操作者的，不算卡住，去回答它。卡住的 agent 马上换掉，不要等它的停止落地。一次巡检如果改变了操作者该知道的事，结束时按 **ketchup** skill 把操作者补上。什么都没变，就保持安静。
7. **操作者一喊停，立刻停下。** 暂停以零写入的命令送到每个负责人。各自报告停在哪里，简报留着，直到操作者放行。

**回复：** 按 **ketchup** skill 把操作者补上。写上每个 PR 的状态和 verdict、合并了什么、会签及原因、还等着操作者的关卡，并附上每个 PR 和决策记录的链接。

# Model the Domain

把真实的领域建模成一个数据结构，而不是把它散落在各种条件分支里。与领域相符的结构能让非法状态无法表示，并删掉分支。写代码时就选好它，代价很低。事后再补，看起来像重构，便一拖再拖。

优先考虑：

- 用状态机，而不是散落的布尔值、阶段标记或生命周期检查。
- 用带类型的模型，而不是松散的参数或重复的形态假设。
- 用 map、注册表、查找表或可区分联合，而不是散落在多个文件里的分支。
- 用 reducer 或命令/事件模型，而不是随意的状态修改。
- 让模块围绕一整套领域知识来组织，而不是围绕「加载、校验、转换、保存」这类顺序。执行顺序不等于归属。
- 用一个小模块边界，把重复的行为、归属或不变量收拢起来。
- 在访问模式需要时，用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。都不合适时，先弄清这段代码**绝不**允许什么、数据会被怎样读取，再去找一个恰好把这些编码进去的结构。

不要硬套抽象。如果当前形态已经清晰、局限在一处、也不太可能长大，那就宁可写平淡无奇的代码。对那些只增加一层间接、却没消掉分支、重复规则、非法状态或生命周期风险的抽象，要心存怀疑。

漏掉这一步的信号是：加新功能时给现有的 if/else 链又续上一个分支，或者多出一个**必须**和第一个保持同步的布尔值。按时间顺序分解是另一个信号。以阶段命名的模块会在各个步骤里重复同一套领域规则。
